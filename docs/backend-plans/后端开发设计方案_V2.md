## 版本变更说明

### V1 → V2 核心变化

| 决策项 | V1 方案 | V2 方案 | 变更原因 |
|--------|---------|---------|---------|
| **任务队列** | PostgreSQL + ARQ | **Celery + Redis** | 成熟可靠，生态完善，支持重试/定时/监控 |
| **事件总线** | PostgreSQL + 单 Worker Queue | **Redis Streams** | 低延迟流式推送，天然支持消费者组 |
| **异步架构** | PGJobQueue + PGWorker | **Celery Worker + Streams Consumer** | 任务调度与事件推送分离，各司其职 |

**架构演进**: PG Queue → Celery Queue + Streams Events

## 0. 文档说明

### 0.1 本方案定位

EasyRAG 前端（Vue3 + Pinia + Element Plus + Vue Flow）已完成 12 个模块的全 mock 实现。本方案是**后端架构升级方案**，目标：

- **架构升级**: 从 PostgreSQL 队列升级为 **Celery + Redis Streams 混合架构**
- **全模块蓝图**: 对齐 V1 已完成的 8 个模块，标注 V2 架构变更点
- **平滑迁移**: 提供从 PG Queue 到 Celery/Streams 的渐进式升级路径

### 0.2 与前端契约对齐

后端 API **严格对齐前端已定义的契约**，不做破坏性改动：

| 契约点 | 前端约定 | 后端实现 |
|--------|---------|---------|
| 基础路径 | `/api/v2` | 一致 |
| 统一响应 | `{ code, message, data }`，`code===0` 成功 | 一致 |
| 认证 | `Authorization: Bearer <jwt>`，40100-40199 触发 refresh | 一致 |
| 流式 | SSE（`@microsoft/fetch-event-source`，POST） | `/chat`、`/executions/:id/stream` |
| 错误码 | 4xxxx / 5xxxx 分段 | 一致（见附录 A） |

## 3. 核心组件设计

### 3.1 Celery 任务队列

```python
# app/core/celery_app.py
from celery import Celery

celery_app = Celery(
    "easyrag",
    broker="redis://localhost:6379/0",
    backend="redis://localhost:6379/1",
    include=[
        "app.worker.tasks.parse_tasks",
        "app.worker.tasks.workflow_tasks",
        "app.worker.tasks.agent_tasks",
    ],
)

# 队列路由配置
celery_app.conf.task_routes = {
    "parse.*": {"queue": "parse"},
    "workflow.*": {"queue": "workflow"},
    "agent.*": {"queue": "agent"},
}

# 默认配置
celery_app.conf.update(
    task_serializer="json",
    accept_content=["json"],
    result_serializer="json",
    timezone="Asia/Shanghai",
    enable_utc=True,
    task_max_retries=3,
    task_default_retry_delay=60,
    worker_prefetch_multiplier=1,
    result_expires=3600,
)
```

**任务分类**:

| 队列 | 任务类型 | 特性 | 超时 |
|------|---------|------|------|
| `parse` | 文档解析 | 可重试，IO 密集 | 5min |
| `workflow` | 工作流执行 | 支持 chain/group | 10min |
| `agent` | Agent 对话 | 长时间运行 | 30min |
| `default` | 其他 | 通用 | 2min |

### 3.2 Redis Streams 事件总线

```python
# app/core/redis_streams.py
class RedisEventBus:
    """Redis Streams 事件总线"""
    
    async def publish(self, stream: str, event: Event) -> str:
        """XADD 发布事件"""
        return await redis.xadd(
            stream,
            {
                "type": event.event_type,
                "timestamp": event.timestamp,
                "payload": json.dumps(event.payload),
            },
            maxlen=10000,
            approximate=True
        )
    
    async def subscribe(self, streams: list[str]) -> AsyncGenerator[Event]:
        """XREADGROUP 订阅事件"""
        async for stream, entries in redis.xreadgroup(
            groupname="sse_consumers",
            streams={s: ">" for s in streams},
            block=5000,
        ):
            for msg_id, fields in entries:
                yield parse_event(fields)
                await redis.xack(stream, "sse_consumers", msg_id)
```

**事件流分类**:

| Stream Key | 用途 | 事件类型 | 保留策略 |
|------------|------|---------|---------|
| `parse:{doc_id}` | 文档解析进度 | task_started/progress/completed/failed | 10000条 |
| `workflow:{exec_id}` | 工作流状态 | node_start/complete/paused/error | 10000条 |
| `agent:{chat_id}` | Agent Token 流 | phase/tool_start/tool_end/token/done | 1000条 |

## 4. 模块设计（V2 架构对齐）

### 4.1 文档处理模块

**V1 (PG Queue)**:
```python
# 旧
PGJobQueue.enqueue_task("parse_document", {"doc_id": doc_id})
```

**V2 (Celery + Streams)**:
```python
# 新
from app.core.celery_app import celery_app
from app.core.redis_streams import publish_event

# 1. 提交任务
task = celery_app.send_task(
    "parse_document",
    args=[doc_id, file_key],
    queue="parse",
)

# 2. 任务中发布事件
@app.task(bind=True, max_retries=3)
def parse_document(self, doc_id: int, file_key: str):
    # 开始
    asyncio.run(publish_event(
        f"parse:{doc_id}",
        Event(
            event_type="task_started",
            payload={"doc_id": doc_id, "pct": 0}
        )
    ))
    
    # 解析... 分阶段发布进度
    for step, pct in [("parsing", 20), ("chunking", 60), ("embedding", 90)]:
        asyncio.run(publish_event(...))
    
    # 完成
    asyncio.run(publish_event(
        f"parse:{doc_id}",
        Event(
            event_type="task_completed",
            payload={"doc_id": doc_id, "pct": 100}
        )
    ))
```

### 4.2 工作流执行模块

**V1**: 单 Worker Queue
**V2**: Celery Chain + Streams

```python
# app/worker/tasks/workflow_tasks.py
from celery import chain

@app.task(bind=True)
def execute_workflow(self, exec_id: str, definition: dict):
    """工作流执行任务"""
    # 解析依赖图，构建 Celery Chain
    node_tasks = [
        execute_node_task.s(exec_id, node)
        for node in topological_sort(definition["nodes"], definition["edges"])
    ]
    
    # 提交链式任务
    workflow_chain = chain(*node_tasks)
    return workflow_chain.apply_async()

@app.task
def execute_node_task(exec_id: str, node: dict):
    """执行单个节点"""
    # 发布开始事件
    asyncio.run(publish_event(..., "node_started", ...))
    
    # 执行节点
    result = execute_node(node)
    
    # 发布完成事件
    asyncio.run(publish_event(..., "node_completed", ...))
    
    return result
```

### 4.3 SSE 端点

**V1**: PostgreSQL 事件表
**V2**: Redis Streams

```python
# app/api/v2/sse.py
@router.get("/executions/{execution_id}/stream")
async def stream_execution_events(execution_id: str):
    """订阅执行事件流（Streams 版）"""
    stream_key = f"workflow:{execution_id}"
    
    async def event_generator():
        async for stream, event in event_bus.subscribe([stream_key]):
            data = {
                "event": event.event_type,
                "data": event.payload,
                "timestamp": event.timestamp,
            }
            yield f"data: {json.dumps(data)}\n\n"
    
    return StreamingResponse(
        event_generator(),
        media_type="text/event-stream",
    )
```

## 7. 对比总结

### 7.1 V1 vs V2 架构对比

| 维度 | V1 (PG Queue) | V2 (Celery + Streams) |
|------|---------------|----------------------|
| **任务重试** | ❌ 需自建 | ✅ Celery 内置 |
| **死信队列** | ❌ 无 | ✅ Celery 支持 |
| **定时任务** | ❌ 无 | ✅ Celery Beat |
| **监控** | ❌ 需自建 | ✅ Flower |
| **SSE 延迟** | 高（轮询/LISTEN） | 低（<10ms） |
| **扩展性** | 中（SKIP LOCKED） | 高（无锁消费） |
| **复杂度** | 低 | 中 |
| **生态** | 弱 | 强 |

### 7.2 何时保持 V1

- 任务量小（<1000/天）
- 不需要重试机制
- 延迟不敏感
- 团队熟悉 PostgreSQL

### 7.3 何时升级到 V2

- 任务量大（>10000/天）
- 需要可靠重试
- 实时流式输出
- 多 Worker 扩展

## 8. 注意事项

1. **Redis 内存**: Streams 设置 `maxlen` 防止无限增长
2. **ACK 机制**: 消费者需手动 ACK，避免消息丢失
3. **连接池**: Redis 连接需合理复用
4. **错误处理**: Celery 任务失败时需发布错误事件
5. **优雅关闭**: Worker 需处理 SIGTERM，完成当前任务
